# GC9A01 programming summary

Source: GalaxyCore, *GC9A01A a-Si TFT LCD Single Chip Driver, 240RGBx240 Resolution*, Data Sheet Rev. 1.0
Preliminary, 2019-07-02 (document LCD-DST-3014, `GC9A01.pdf`, 192 pages). The GC9A01 is the controller of the
1.28" round 240 x 240 modules. It implements the MIPI DCS user commands and is driven by the generic head
`src/head/MIPI_DCS.h` (`MIPI_DCS_GC9A01`); the shared head description is in `MIPI_DCS.md`, this file holds
everything that is specific to the GC9A01. The datasheet is a preliminary copy of a 240 x 320 driver datasheet in
many places (GRAM size, CASET defaults, B3h, EXTC references); those contradictions are pointed out where they
matter. Page numbers are PDF pages.

The RGB interface needs one of the serial modes for the commands. The text of 4.5.4 / 4.5.6 quotes other IM codes
("0000" for the 8080-I 8 bit, "0001" for 16 bit, "1000" for 8080-II 16 bit) that contradict Table 6; Table 6 and

### 2.2 8080 parallel (4.1.2 .. 4.1.7, p. 22 .. 27)

`CSX`, `D/CX` (0 command, 1 parameter / GRAM data), `WRX` (data latched on the rising edge), `RDX` (data valid
at the rising edge), `D[17:0]`. Reads return one invalid (dummy) word after the command, then valid data; with
D/CX low during a read the bus stays Hi-Z (p. 24). Pixel transfers (4.5.4 .. 4.5.7):

| Bus | 16 bit / pixel (3Ah DBI = 101) | 18 bit / pixel (DBI = 110) |
|---|---|---|
| 8 bit | 2 transfers: R4..R0 G5..G3, then G2..G0 B4..B0 | 3 transfers, 6 bits per byte |
| 9 bit | 2 transfers per pixel (4 transfers for 2 pixels) | |
| 16 bit | 1 transfer RGB565 | 2 transfers, 4 layouts selected by MDT[1:0] (the register holding MDT is not documented; F6h lists MDT only in its default table) |
| 18 bit | 1 transfer | 1 transfer R5..B0 on D17..D0 |

### 2.3 Serial interface (4.1.8 .. 4.1.10, p. 28 .. 32; 4.5.1 .. 4.5.3, p. 45 .. 51)

MSB first, SDA sampled on the rising edge of SCL, SDO / SDA output changes on the falling edge, so SPI mode 0
(or 3) works. A falling CSX starts a transfer; CSX may go high between bytes and between command and parameters.

- 4 line: the D/CX pin selects command (0) or data (1) per byte, 8 bit frames.
- 3 line: 9 bit frames, the first bit is D/CX, then D7 .. D0.
- Reads (interface I on SDA, II on SDO): 8 bit reads (DAh .. DCh, and the figure also names 0Ah .. 0Fh) follow
  the command directly; 24 bit (04h) and 32 bit (09h) reads have one dummy clock before the data (Figures 14 ..
  19). The command descriptions themselves say "the first parameter is dummy data", which is the parallel bus view.
- Break and recovery (4.1.11, p. 33): a CSX pulse in the middle of a byte discards the partial byte; a RESX pulse
  aborts the command, wait more than 10 us after RESX before the next transfer. Parameters already received are
  kept when a multi parameter command is interrupted by a new command.

Pixel layouts on the serial bus (4 line shown, 3 line identical with the D/CX bit = 1 in front of each byte):

| COLMOD | Bytes | Layout |
|---|---|---|
| 03h 12 bit (DBI 011) | 3 bytes per 2 pixels | R1[3:0] G1[3:0], B1[3:0] R2[3:0], G2[3:0] B2[3:0] |
| 55h 16 bit (DBI 101) | 2 | R4..R0 G5..G3, G2..G0 B4..B0; expanded to 18 bit through a look up table |
| 66h 18 bit (DBI 110) | 3 | R5..R0 x x, G5..G0 x x, B5..B0 x x (6 bits left aligned) |

2 data line mode (4.5.3, p. 50; E9h): only pixel data use two lines, commands and parameters stay 3 line. Each
transfer is a flag bit A0 = 1 followed by the data, with the high part on SDA and the low part on DCX in
parallel: `000` RGB565 (SDA: R4..R0 G5..G3, DCX: G2..G0 B4..B0), `001` RGB666 1 pixel / transfer, `010` RGB666
2/3 pixel / transfer, `100` RGB888 1 pixel / transfer, `110` RGB888 2/3 pixel / transfer.

### 2.4 RGB and VSYNC interface (4.2, 4.3, p. 38 .. 45)

RCM[1:0] (B0h) = 10 DE mode (VSYNC, HSYNC, DE, DOTCLK), 11 SYNC mode (DE ignored, porches from B5h); RIM (F6h)
= 0 18 bit (D[17:0]) or 16 bit (D[17:13], D[11:1]) in one transfer, 1 6 bit (D[5:0]) in 3 transfers; DM (F6h)
selects internal clock / RGB / VSYNC operation, RM = 1 routes GRAM writes from the RGB port. All sync signals are
sampled on the rising DOTCLK edge, VSYNC / HSYNC low active, DE high active (defaults, B0h polarity bits).
Table 10 (p. 39) is copied from a 320 pixel part (HAdr 320, VAdr 240). Partial, scroll and interlace are not
available in VSYNC mode.

## 3 Frame memory and pixel formats

Every 18 bit pixel has an address (page, column) = (y, x). CASET (2Ah) and RASET (2Bh) define a window, RAMWR (2Ch)
resets the pointer to (SC, SP) and writes; the column counter increments per pixel, wraps to SC after EC with the
page incremented, and wraps to (SC, SP) after (EC, EP) (5.2, p. 71). WRMEMC (3Ch) continues after the last pixel
written; with MV = 1 the page counter runs first. Any command ends a write. MADCTL MY / MX / MV decide which
physical counter CASET / RASET address and whether it counts down (`239 - pointer`), so the window is always given
in the rotated coordinate system. In normal mode GRAM columns 0 .. EFh and pages 0 .. EFh are shown; pixel (0, 0)
is the top left corner (5.3.1).

COLMOD (3Ah, p. 135): `0 DPI[2:0] 0 DBI[2:0]`, reset 66h.

| DBI[2:0] (MCU) | DPI[2:0] (RGB) | Format |
|---|---|---|
| 011 | reserved | 12 bit / pixel RGB444 |
| 101 | 101 | 16 bit / pixel RGB565 (3Ah = 55h) |
| 110 | 110 | 18 bit / pixel RGB666 (3Ah = 66h) |
| others | others | reserved |

There is no 24 bit format on the MCU interface (RGB888 only in the 2 data line mode). The read format of the
GRAM is not documented because RAMRD (2Eh) has no description (it is only named in the text of 5.1 / 5.2).

## 5 Orientation

MADCTL (36h, p. 127; 5.2, p. 71):

| Bit | Name | Meaning |
|---|---|---|
| D7 | MY | row address order: the page counter runs 239 -> 0 (vertical mirror) |
| D6 | MX | column address order: the column counter runs 239 -> 0 (horizontal mirror) |
| D5 | MV | row / column exchange: CASET addresses the physical pages, RASET the physical columns |
| D4 | ML | vertical refresh order (panel scan direction, image unchanged) |
| D3 | BGR | 0 RGB, 1 BGR colour filter, takes effect immediately without rewriting the GRAM |
| D2 | MH | horizontal refresh order |
| D1, D0 | - | 0 |

Reset 00h; a software reset leaves MADCTL unchanged. B6h SS / GS mirror the panel outputs in addition (both 0
by default, the head leaves them 0).

| `orientation_0` | - | 08h | 240 x 240 |
| `orientation_0m` | MY | 88h | 240 x 240 |
| `orientation_180` | MX, MY | C8h | 240 x 240 |
| `orientation_180m` | MX | 48h | 240 x 240 |

Offsets: the round panel covers the whole 240 x 240 GRAM and the mirrored counters use 239 as the end on both
axes, so `Offset_X = Offset_Y = 0` in every orientation. The panel is round, the GRAM corners outside the circle are
simply not visible. Whether a module needs BGR and inversion is a panel property the datasheet does not state; the
head defaults to BGR = 1 and INVON for the GC9A01 modules.

## 6 Power, reset and sequences

The datasheet has no power on / off timing figure, no reset pulse table and no recommended initialisation
sequence. What it states:

- Supplies: IOVCC must not exceed VCI (7.2 note 2). Power off mode = both supplies removed (5.10.1).
- Reset: RESX is low active and "must be applied to properly initialize the chip" (pin table p. 10); after a RESX
  pulse wait more than 10 us before the next transfer (Figure 20, p. 33). During power on the inputs are invalid,
  after power on / hardware reset the outputs are Hi-Z, TE and LEDPWM low (5.11, p. 90).
- After reset the controller is in sleep in, display off (section 1).
- SLPOUT: wait 5 ms before the next command; display shows a blank screen for 2 frames automatically. SLPIN:
  5 ms before the next command, 120 ms until sleep is reached; SLPIN and SLPOUT must be 120 ms apart (p. 101 .. 104).
- Display off / on (28h / 29h) only blank / unblank, they can be sent at any time.
- Power levels (5.10, p. 87): normal, partial, idle, partial + idle, sleep in (DC/DC, oscillator and panel driver
  stopped, interface and GRAM alive on IOVCC), power off. All transitions between levels 1 .. 5 are by command
  without visible artefacts.

A sequence consistent with these rules: supplies on (IOVCC <= VCI), RESX low (at least 10 us), wait, FEh EFh and
vendor registers, MADCTL, COLMOD, SLPOUT, wait 120 ms, DISPON. Power off: DISPOFF, SLPIN, wait 120 ms, supplies
off.

## 8 The vic head

```cpp
// 1.28" round 240 x 240 module, defaults: BGR, INVON, RGB565, no offsets
vic::head::MIPI_DCS<vic::head::MIPI_DCS_GC9A01, 240, 240> tft(handle);
vic::head::MIPI_DCS<vic::head::MIPI_DCS_GC9A01, 240, 240, vic::drv::orientation_90> tft90(handle);
```

- io layer: `io::write()` option 0 = command byte (D/CX low), 1 = parameters / pixels (D/CX high); `io::read()`
  option 1 for GRAM pixels, see `MIPI_DCS.md`.
- init: the GC9A01 table (below, from the reference drivers), then MADCTL from the orientation table (08h for
  `orientation_0`), COLMOD 55h (66h with `Color_18bit`), INVON (`Invert` defaults to true for the GC9A01) and a
  clear screen. There is no SWRESET in the GC9A01 table; the head relies on the power on / RESX reset done by the
  application or io layer.
- Drawing: window 2Ah / 2Bh / 2Ch in logical coordinates (no offsets), RGB565 big endian, streams of 32 pixels;
  the tracked write pointer matches the counter rules of 5.2.
- `pixel_get()`: 2Eh, then three bytes as 6 bit left aligned R, G, B.
- `display_enable()` 29h / 28h, `display_brightness()` 53h 24h (BCTRL | BL) and 51h level (LEDPWM pin),
  `display_inverse()` relative to the INVON default, `shutdown()` 28h, 10h, 5 ms.

Documented registers in the table: FEh, EFh, B6h, C3h, C4h, C9h, F0h .. F3h, E8h, 35h, 11h, 29h (15 of 47 table
entries). Undocumented: EBh, 84h .. 8Fh, 90h, BCh, BDh, BEh, FFh, E1h, DFh, EDh, AEh, CDh, 70h, 62h, 63h, 64h,
66h, 67h, 74h, 98h. Their values come from the panel vendor's reference code and cannot be checked against this
datasheet.

Discrepancies and open points found in the crosscheck:

1. `pixel_get()` uses RAMRD (2Eh), which the GC9A01 datasheet does not document (no command entry, no read format,
   no dummy cycle definition); the serial read figures only cover 8 / 24 / 32 bit register reads. The 3 byte, 6 bit
   left aligned read format is an assumption carried over from the other DCS controllers. Most round modules wire
   only SDA (interface I), so the io layer must turn SDA around for reads or return false.
2. TEON (35h) is sent without its parameter; harmless (M stays 0), but not as documented. The TE pin is enabled even
   though the head never uses it.
3. The table starts with a lone EFh and an undocumented EBh 14h before the FEh / EFh unlock; per 6.4.8 only the
   FEh, EFh pair sets Inter_command.
4. E8h is written with one parameter; the detailed description has one parameter (DINV[3:0] in bits 7:4), the command
   list two (DINV[2:0], RTN1[3:0] and RTN2[7:0]). Both readings give 4 dot inversion for 34h.
5. No reset in the GC9A01 table (other tables start with SWRESET); 01h is not documented here anyway, so the
   controller depends on the RESX reset before `init()`. A second `init()` without reset works because all
   registers are rewritten, Inter_command simply stays set.
6. `shutdown()` waits 5 ms after SLPIN; that is enough for the next command, but the datasheet needs 120 ms until
   sleep mode is reached, so supplies must not be cut earlier, and a following `init()` (SLPOUT) must come at
   least 120 ms after SLPIN.
7. Head defaults `RGB_to_BGR = true` and `Invert = true` differ from the datasheet reset state (MADCTL 00h,
   inversion off); they are module (panel) properties, not stated in the datasheet.
8. `display_brightness()` (53h 24h, 51h) matches the documented bits, but it drives the LEDPWM pad, which most
   GC9A01 modules leave unconnected (backlight on a separate pin).
9. Datasheet inconsistencies a driver author should not trust: GRAM size 172,800 byte / 320 x 240 (4.4, 5.1) vs
   129,600 byte / 240 x 240 (1, 2); CASET reset end 013Fh and the "013Fh" limits of 2Ah / 2Bh / 30h; B5h VBP default
   08h vs 02h; E8h layout; VGL range; IM codes in the text of 4.5.4 / 4.5.6; B3h / EXTC references copied from
   another chip.
10. `MIPI_DCS.md` lists the GC9A01 interfaces without the 2 data line SPI mode and gives "2.8 .. 3.3 V logic" for all
    controllers; the GC9A01 accepts IOVCC 1.65 .. 3.3 V.
