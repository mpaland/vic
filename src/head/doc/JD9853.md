# JD9853 programming summary

Source: Jadard *JD9853 240RGB x 320 dot, 262K color, with internal GRAM, a-Si TFT LCD Single Chip Driver*,
Preliminary V0.00 (revision history: 2023/2/14 "New setup", page footer April 25, 2023, 163 pages, `JD9853.pdf`).
The JD9853 drives the 1.47" 172 x 320 and 2" 240 x 320 modules (Waveshare ESP32-S3-LCD-1.47 and others). It
implements the MIPI DCS user command set, so it is driven by the generic head `src/head/MIPI_DCS.h`
(`MIPI_DCS_JD9853`); the common parts of that command set and of the head are in `MIPI_DCS.md`, this file holds
what is specific to the JD9853. The datasheet is preliminary: the whole "user command" (vendor register) chapter
is "TBD", several standard commands are missing and some tables are copied from a 128 x 160 controller; these
points are marked below.

## 1 Overview

| Item | Value |
|---|---|
| Panel | 240 RGB x 320, 720 source (S1..S720) and 320 gate (G1..G320) channels, normally a-Si TFT |
| GRAM | 240 x 320 x 18 bit = 172,800 byte (1,382,400 bit) |
| Supplies | IOVCC 1.65 .. 3.3 V (logic / interface), VCI 2.6 .. 3.3 V (analog), VPP 8.25 V for OTP programming only; internal DC/DC for the panel voltages (AVDD, AVEE, VGH, VGL, VCL), internal VDDD 1.5 V |
| Interfaces (IM[3:0]) | 8080 parallel 8 / 9 bit, 3 line 9 bit SPI (I and II), 4 line 8 bit SPI (I and II), 2 data lane SPI, QSPI, RGB (DPI) 6 bit with DE or HV mode, VSYNC interface |
| Colors | 262k (18 bit) in the GRAM, 16 bit RGB565 and 18 bit RGB666 per pixel on every MCU interface (also on SPI), 8 colors in idle mode |
| OTP | the vendor register settings are stored in the OTP, the host does not need to send them (gamma 1 time, VGMP/VGSP/VGMN/VGSN 3 times, ID 2 times programmable) |
| Extras | partial area, vertical (and horizontal) scrolling, tearing effect line, idle mode, 2 lane / quad SPI data transmission, sunlight readability (SLR), dot / column inversion, LEDPWM / LEDON backlight outputs, internal 10 MHz +-5 % RC oscillator |
| State after HW reset | sleep in, display off, normal mode on, idle off, inversion off, TE off, MADCTL 00h, COLMOD 06h (18 bit), window 0..EFh x 0..13Fh, GRAM content random |

Correction to the earlier version of this file: the datasheet (features p. 10, IM table p. 18) has a 9 bit data
bus only (DB[8:0]), so there is no 16 / 18 bit 8080 bus, and the RGB interface is 6 bit (DB[5:0], 65k or 262k,
p. 52), not 16 / 18 bit. COLMOD also lists a 12 bit code (011) but no interface defines a 12 bit data format.

## 2 Interfaces

### 2.1 Interface selection (6.2, p. 18; 7.1.1, p. 22)

| IM3 IM2 IM1 IM0 | Interface | Data pins |
|---|---|---|
| 0000 | 8080 8 bit parallel I | DB[7:0] |
| 0010 | 8080 9 bit parallel I | DB[8:0] |
| 0100 | Quad serial interface (QSPI) | SDA in/out, DB[2:0] in |
| 0101 | 3 line 9 bit serial interface I, or 2 data lane serial interface (after D7h = 20h), RGB interface commands | SDA in/out (+ WRX in for the second lane) |
| 0110 | 4 line 8 bit serial interface I | SDA in/out |
| 1101 | 3 line 9 bit serial interface II | SDA in, SDO out |
| 1110 | 4 line 8 bit serial interface II | SDA in, SDO out |

The table in 7.1.1 omits the QSPI row, the pin table in 6.2 has it. The RGB interface needs a serial
interface for the commands (IM = 0101 recommended, p. 52).

Pins: `CSX` (chip select, low active, signals are ignored while high), `RESX` (reset, low active), `DCX_SCL`
(D/CX on the 8080 bus, SCL on the serial buses), `WRX` (8080 write strobe, D/CX of the 4 line SPI, second data
lane of the 2 lane SPI), `RDX` (8080 read strobe), `DB[8:0]` (8080 / RGB data, QSPI lanes DB[2:0]), `SDA`, `SDO`,
`TE` (tearing effect output), `PCLK`, `VSYNC`, `HSYNC`, `DE` (RGB), `LEDPWM` (backlight PWM output), `LEDON`
(backlight enable output). Unused inputs go to IOVCC or GND, unused outputs stay open.

### 2.2 8080 parallel bus (7.1.2, p. 23)

`D/CX` = 0 command, 1 parameter / GRAM data. A write is latched on the rising edge of `WRX`, a read is sampled by
the host on the rising edge of `RDX`. Every read (register or GRAM) starts with one dummy read, then the data
bytes; with D/CX low during a read the outputs stay Hi-Z. Parameters and register reads are 8 bit on DB[7:0];
the 9 bit bus carries 9 bit pixel data on DB[8:0].

### 2.3 3 line and 4 line SPI (7.1.3, p. 26 .. 31)

4 line SPI: `CSX`, `D/CX` (0 command, 1 parameter / data), `SCL`, `SDA`, MSB first, data latched on the
rising edge of SCL. 3 line SPI: 9 bit frames with the D/CX bit first. The serial interface II variants
have a separate `SDO` for reads, interface I reads on `SDA`. On the JD9853 the D/CX signal of the 4 line SPI is
the `WRX` pin and SCL is the `DCX_SCL` pin (pin description p. 27). The output data is shifted on the falling edge
of SCL; the host must release SDA (Hi-Z) no later than the falling edge of the last command bit. A falling CSX
starts a transfer, CSX high resets the serial state machine.

Read format on the serial interfaces (figures 7.9, 7.10): 8 bit reads (0Ah .. 0Fh, DAh .. DCh) return the data
byte directly after the command, the 24 / 32 bit reads (04h, 09h) insert one dummy clock before the data. On the
parallel bus all reads start with a dummy byte instead. Reads on SPI therefore return a dummy byte / clock before
the first data byte of the multi byte reads; the GRAM read (RAMRD) is not described (section 4.1).

Break and pause (7.1.5, 7.1.6): a byte interrupted by CSX high before D0 is discarded and has to be resent;
parameters already received are stored, the interrupted one is rejected. CSX may go high after any complete
byte (command or parameter or pixel byte), the transfer continues where it stopped.

### 2.4 2 data lane SPI (7.1.4, p. 33)

IM = 0101 and register D7h = 20h. Commands and parameters use the 3 line 9 bit protocol on SDA (WRX ignored),
reads too. Pixel data goes out on SDA and WRX simultaneously, each lane a D/CX = 1 frame: RGB565 as two 9 bit
frames (SDA: 1, R4..R0, G5..G3; WRX: 1, G2..G0, B4..B0), RGB666 as two 10 bit frames (SDA: 1, R5..R0, G5..G3;
WRX: 1, G2..G0, B5..B0) per pixel (7.1.8.3, p. 43, 44).

### 2.5 Quad SPI (7.1.3, p. 29, 32; 7.1.8.4, p. 45, 46)

IM = 0100, lanes `SDA`, `DB[0]`, `DB[1]`, `DB[2]` = bit 0 .. bit 3 of each nibble. Every transfer starts with
an instruction byte on SDA, then a 24 bit address whose middle byte is the DCS command (`00h, cmd, 00h`, e.g.
`002C00h` for RAMWR), then the data:

| Instruction | Use |
|---|---|
| 02h | register write and 1 lane pixel data (address and data on SDA) |
| A2h | pixel data on 2 lanes (SDA, DB[0]; DB[0] carries the upper bit of each pair) |
| 32h | pixel data on 4 lanes (address on SDA, data nibbles on DB[2:0] + SDA) |
| 38h | address and pixel data on 4 lanes, only the command byte (2Ch or 3Ch) is sent as AD[7:0] |
| 03h | register read, data returned on SDA (or SDO) after the address |

RGB565 is 2 bytes per pixel, RGB666 3 bytes (6 bits left aligned, 2 zero bits). The section title of the 18 bit
QSPI format says "65,536 colors", a typo.

### 2.6 RGB and VSYNC interfaces (7.2, 7.3, p. 52 .. 58)

6 bit RGB only (DB[5:0], 3 PCLK per pixel), selected by RGB_SEL[1:0] = 11 plus COLMOD DPI = 110 (262k) or 101
(65k); RGB_SEL is a vendor register field that is not located in the datasheet. DE mode or HV mode and the data
path (GRAM or shift register, i.e. without RAM) are selected with B1h (DEM, DM[1:0]), also undocumented.
Porch limits: HS 6 .. 24 clocks, HBP >= 12, HS + HBP <= 252, HFP >= 6, VS / VBP / VFP >= 1 line, VS + VBP <= 126,
HS / HBP / HFP must be min + n x 3 clocks. Partial display and scrolling are not available in RGB mode. The VSYNC
interface (8080 writes synchronised by VSYNC) is enabled with DM[1:0] = 10 and RM = 1.

### 2.7 Pixel data layouts (7.1.8, p. 39 .. 51)

| Interface | 3Ah | Transfers per pixel |
|---|---|---|
| 3 line SPI | 05h / 55h | 2 frames: [1, R4..R0, G5..G3] [1, G2..G0, B4..B0] |
| 3 line SPI | 06h / 66h | 3 frames: [1, R5..R0, x, x] [1, G5..G0, x, x] [1, B5..B0, x, x] |
| 4 line SPI | 05h / 55h | 2 bytes: R4..R0 G5..G3, G2..G0 B4..B0 |
| 4 line SPI | 06h / 66h | 3 bytes, 6 bits left aligned (D7..D2) per color |
| 8080 8 bit | 05h / 55h | 2 bytes like the 4 line SPI |
| 8080 8 bit | 06h / 66h | 3 bytes like the 4 line SPI |
| 8080 9 bit | 05h / 55h | 2 bytes on D7..D0 (D8 don't care) |
| 8080 9 bit | 06h / 66h, MDT = 00 | 2 x 9 bit: R5..R0 G5..G3, G2..G0 B5..B0 |
| 8080 9 bit | 06h / 66h, MDT = 01 | 3 bytes, 6 bits on D7..D2 (MDT location undocumented) |

16 bit pixels are expanded to 18 bit by a lookup table (R and B LSB from the MSB). The 8 bit RGB565 diagram labels
the red bits "Bit 5 .. Bit 1" while its note says red is Bit 4 .. Bit 0; the note is the usual RGB565 layout.

Input rise / fall times <= 15 ns on the 8080 bus.

## 3 Frame memory and pixel formats

GRAM (0, 0) is the top left pixel of the panel with MADCTL = 00h, 240 columns x 320 rows (pages). The text of 8.1.1
(p. 59) and the CASET / PASET restrictions speak of 00h .. 7Fh / 00h .. 9Fh; that is copied from a 128 x 160 chip,
the defaults (00EFh / 013Fh) and the figures show the 240 x 320 range.

| Hex | Name | Parameters | Reset |
|---|---|---|---|
| 2Ah | CASET | SC[15:0], EC[15:0], SC <= EC | 0000h .. 00EFh (MV = 1: 013Fh after HW reset) |
| 2Bh | PASET | SP[15:0], EP[15:0], SP <= EP | 0000h .. 013Fh (MV = 1: 00EFh after HW reset) |
| 2Ch | RAMWR | pixel data, any length | pointer to (SC, SP) |
| 3Ch | WRMEMC | pixel data | continues after the last written pixel |

Pointer movement (8.2, p. 64): RAMWR (or RAMRD) resets the column and page counters to the start column / page;
every complete pixel increments the column; past EC the column returns to SC and the page increments; past EP
both return to the start. Only complete pixels are stored, odd pixel counts are allowed. Extra pixels beyond
(EC - SC + 1) x (EP - SP + 1) of a WRMEMC are ignored. The window is given in the coordinate system that MADCTL
MV / MX / MY produce (section 5). Data transfer method 1 streams frame after frame after one RAMWR, method 2 sends
a new RAMWR per frame (7.1.7, p. 38).

COLMOD (3Ah, 9.2.30, p. 143):

| Bits | Field | Codes |
|---|---|---|
| D6:D4 | DPI, RGB interface color format | 101 = 16 bit, 110 = 18 bit (011 = 12 bit listed, no data format) |
| D2:D0 | DBI, MCU interface color format | 011 = 12 bit, 101 = 16 bit, 110 = 18 bit |

| DBI[2:0] (MCU) / DPI[2:0] (RGB) | Format |
|---|---|
| 011 | 12 bit per pixel (RGB444) |
| 101 | 16 bit per pixel (RGB565) |
| 110 | 18 bit per pixel (RGB666) |

Reset value: 06h, 18 bit on the MCU interface (RDDCOLMOD p. 104; the earlier version of this file said 66h); SW
reset leaves it unchanged. The interface chapters write the formats as 3Ah = 05h / 06h; 55h / 66h set the RGB
field too and are equally valid. The SPI interface runs the 16 bit RGB565 format (COLMOD 55h), unlike the ILI9488.

Partial mode (12h, 30h) shows the rows SR .. ER and blanks the rest; vertical scrolling (33h, 37h) needs
TFA + VSA + BFA = 320 (otherwise undefined) and MV = 0 for the writes; with SCR_SEL = 1 the same registers define a
horizontal scroll of the columns (fixed left / scroll / fixed right).

them (apart from the D7h value for the 2 lane mode) is described in the datasheet; their meaning and the
password / page mechanism are known only from that code. The OTP programming procedure (VPP 8.25 V) is not
described either.

## 5 Orientation

MADCTL (36h, 9.2.26, p. 136):

| Bit | Name | Meaning |
|---|---|---|
| D7 MY | page address order | 1: rows from bottom to top (PASET maps to 319 - row) |
| D6 MX | column address order | 1: columns from right to left (CASET maps to 239 - column) |
| D5 MV | page / column exchange | 1: CASET addresses the physical rows, PASET the physical columns |
| D4 ML | vertical refresh order | panel refresh direction, no effect on the image (affects scroll / partial direction) |
| D3 BGR | color order | 0 = RGB, 1 = BGR color filter panel |
| D2 MH | horizontal refresh order | panel refresh direction, only implemented for pixel by pixel refresh |
| D1 SS / D0 GS | source / gate scan flip | listed in the description, but "D1 and D0 are set to 00 internally" and the command list shows 0 |

MY (B7), MX (B6), MV (B5), ML (B4), BGR (B3), MH (B2) have the same meaning as on the other DCS controllers.
Reset value 00h (HW reset), SW reset leaves it unchanged.

vic orientations (`MIPI_DCS.h` MADCTL table) and the panel offsets of the 1.47" 172 x 320 module:

| Orientation | MADCTL bits | Logical size 240 x 320 / 172 x 320 module | Offset_X, Offset_Y (172 x 320) |
|---|---|---|---|
| `orientation_0` | - | 240 x 320 / 172 x 320 | 34, 0 |
| `orientation_0m` | MY | 240 x 320 / 172 x 320 | 34, 0 |
| `orientation_180` | MX, MY | 240 x 320 / 172 x 320 | 34, 0 |
| `orientation_180m` | MX | 240 x 320 / 172 x 320 | 34, 0 |
| `orientation_90` | MX, MV | 320 x 240 / 320 x 172 | 0, 34 |
| `orientation_90m` | MX, MY, MV | 320 x 240 / 320 x 172 | 0, 34 |
| `orientation_270` | MY, MV | 320 x 240 / 320 x 172 | 0, 34 |
| `orientation_270m` | MV | 320 x 240 / 320 x 172 | 0, 34 |

The BGR bit is added by the head when `RGB_to_BGR` is set.

The 1.47" 172 x 320 module is centred on the 240 GRAM columns: CASET 22h .. CDh, i.e. `Offset_X = 34`
for `orientation_0` / `orientation_0m`; with MX set (`orientation_180`, `orientation_180m`) the offset is
also 34 (240 - 172 - 34), with MV set the offset moves to the rows (`Offset_Y = 34`). The 2" 240 x 320
module needs no offset. The reference code sends MADCTL 00h and no inversion, so the modules match the
datasheet default (`orientation_0`, `RGB_to_BGR = false`, `Invert = false`). The 320 rows always match the panel,
so MY never changes an offset.

## 6 Power, reset and sequences

Power on (datasheet 8.7, p. 85, 86): IOVCC first, then VCI, tPWON = 5 ms; no limit on the rise times. Then a
reset pulse: RESX low >= 10 us (TRESETL), placed tRPWIRES >= 10 ms after the supplies are up; wait 5 ms after the
rising RESX edge (5 ms after a software reset), then either

- option 1: the initial settings followed by SLPOUT (page 0 11h), 120 ms, DISPON (29h), or
- option 2, with the settings in the OTP: SLPOUT and DISPON only, 120 ms after SLPOUT before DISPON.

The earlier version of this file read the figure as ">= 10 ms after the reset"; the figure puts the 10 ms between
power and reset and the 5 ms after the reset. If RESX is not held stable during power on, a HW reset is required
after the supplies are up.

Reset (10.3.6, p. 163): pulses < 5 us are rejected, 5 .. 10 us may start a reset, > 10 us reset. Reset complete
time tRT 5 ms when reset in sleep in, 120 ms when reset in sleep out (the display runs a blanking sequence of up to
120 ms). Commands 5 ms after RESX high, SLPOUT not before 120 ms.

| Command | Wait / rule (9.2) |
|---|---|
| SWRESET | 5 ms before the next command; in sleep in 120 ms before SLPOUT; "should not be sent when the module is not in SLPIN mode" (wording as printed, p. 94) |
| SLPOUT | 5 ms before the next command, 120 ms before SLPIN; 120 ms before DISPON in the power on figure; panel shows blank for 2 frames |
| SLPIN | 5 ms before the next command, 120 ms after SLPOUT; sources blank for 2 frames, then discharge, DC/DC and oscillator stop |
| DISPON / DISPOFF | no wait specified |

Power off (p. 87): option 1: RESX low, 120 ms, then VCI off, IOVCC afterwards (no limit). Option 2: DISPOFF,
SLPIN, 120 ms, then RESX low / VCI off, IOVCC afterwards. In sleep out VCI and IOVCC go down >= 120 ms after the
reset, in sleep in 0 ms. IOVCC goes on first and off last. Power off: DISPOFF, SLPIN, then VCI and IOVCC off.
Sleep mode keeps the GRAM. There is no damage if the sequences are not met.

Power levels (8.6): normal / partial x idle on / off with sleep out, sleep in (interface and GRAM on IOVCC, contents
safe), power off (both supplies removed). All transitions except power off are command controlled.

## 8 The vic head

```cpp
// 1.47" 172 x 320 module, portrait
vic::head::MIPI_DCS<vic::head::MIPI_DCS_JD9853, 172, 320, vic::drv::orientation_0, false, false, false, 34, 0> tft(handle);
// 2" 240 x 320 module, landscape
vic::head::MIPI_DCS<vic::head::MIPI_DCS_JD9853, 320, 240, vic::drv::orientation_90> tft2(handle);
```

Init table `MIPI_DCS_init::JD9853`:

```
01h, delay 5 ms      software reset
11h, delay 120 ms    sleep out
13h                  normal display mode on
29h, delay 20 ms     display on
```

- init: SWRESET (120 ms), SLPOUT (120 ms), NORON, DISPON (20 ms), then MADCTL from the orientation, COLMOD 55h,
  INVOFF and a clear screen. Everything else is in `MIPI_DCS.md`. The hardware reset is the io layer's job.
- Template defaults for `MIPI_DCS_JD9853`: `RGB_to_BGR = true` (default of all controllers but the ST7789),
  `Invert = false`, `Color_18bit = false` (COLMOD 55h, 66h with `Color_18bit`), offsets 0 / 0.
- Drawing: CASET / PASET (the head calls it RASET, same 2Bh) / RAMWR with the offsets added, RGB565 big endian (or
  3 bytes with 6 bits left aligned), streamed in blocks of 32 pixels; the head tracks the write pointer along x.
- `pixel_get()`: one pixel window, RAMRD (2Eh), three bytes with 6 bits left aligned, the io layer handles the dummy;
  `color::none` without read support.
- `display_enable()` = 29h / 28h, `display_brightness()` sends nothing (no 51h / 53h), `display_inverse()` =
  21h / 20h, `shutdown()` = 28h, 10h, 120 ms.
- Not covered: the 2 lane SPI / QSPI data transmission (D7h), the RGB interface, partial / scroll / idle
  modes, the tearing effect line, the vendor registers.

Crosscheck against the datasheet:

| Head use | Datasheet | Result |
|---|---|---|
| SWRESET, 120 ms | 5 ms before the next command, but 120 ms before SLPOUT when sent in sleep in (always the case after power on / HW reset or after `shutdown()`) | ok (was 5 ms) |
| SLPOUT, 120 ms | 5 ms before the next command, 120 ms before DISPON (8.7.2) | ok |
| NORON, no delay | no wait; normal mode is already the reset state | ok, redundant |
| DISPON, 20 ms | no wait specified | ok |
| MADCTL MY / MX / MV / BGR | documented, reset 00h | ok |
| COLMOD 55h / 66h | 16 / 18 bit on all MCU interfaces, DPI field ignored by SPI | ok; the 2 lane / QSPI bit layouts differ and need an io layer that packs them |
| INVOFF | reset state is inversion off, reference sends none | ok |
| CASET / PASET values | EC <= EFh, EP <= 13Fh (MV = 0) | ok, the offsets keep the 172 x 320 window inside |
| RAMRD in `pixel_get()` | 2Eh is not documented, read format unknown | unverified |
| `display_brightness()` | 53h / 51h not documented | sends nothing (sent 53h / 51h before) |
| SLPIN + 120 ms in `shutdown()` | 5 ms before the next command; 120 ms before removing VCI / IOVCC | ok (was 5 ms) |

Discrepancies found (1, 3 and 4 are fixed in the head):

1. Fixed: SWRESET waited 5 ms, then SLPOUT followed; 9.2.2 asks for 120 ms between a SWRESET in sleep in mode and SLPOUT,
   and 10.3.6 asks for 120 ms after a HW reset before SLPOUT. Modules started reliably in practice, the head now
   waits the datasheet value of 120 ms. The same restriction text says SWRESET should only be sent in sleep in, so `init()` on a
   running display (sleep out) is outside the datasheet.
2. `pixel_get()` uses RAMRD (2Eh), which the preliminary datasheet does not document (no command list entry, no
   description, RDMEMC 3Eh likewise missing); the 18 bit read format and the dummy byte / clock are assumed from the
   other DCS controllers.
3. Fixed: `display_brightness()` sent 53h / 51h, which are not in the JD9853 command set, it sends nothing now; the
   LEDPWM pin exists but its control registers are undocumented.
4. Fixed: `shutdown()` waited 5 ms after SLPIN; power off option 2 requires 120 ms after SLPIN before VCI / IOVCC
   are removed, the head waits 120 ms now.
5. The head's `RGB_to_BGR` default is `true` for the JD9853, while the reference code sends MADCTL 00h (RGB); the
   1.47" example passes `false` explicitly, the 2" example uses the default and therefore sets BGR.
6. Datasheet inconsistencies to keep in mind: ID3 01h (04h) vs 00h (DCh); COLMOD reset 06h; MADCTL D1 / D0 listed
   but forced to 0; 7Fh / 9Fh address limits copied from a 128 x 160 part; QSPI 18 bit title says 65k colors.
